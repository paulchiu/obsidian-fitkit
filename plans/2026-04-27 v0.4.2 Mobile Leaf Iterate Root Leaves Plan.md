## 1. Goal & Success Criteria

When the user runs `Open today's workout` or `Open workout editor for current file` on Obsidian Mobile, the editor opens in the main area (`workspace.rootSplit`) by default, not in a side drawer. A leftover drawer leaf from a previous install (the user's current state) is detached and replaced by a fresh main-area tab.

**Definition of done for 0.4.2:**

- On Obsidian Mobile (real device, manual smoke), running `Open today's workout` from a clean state opens the editor in the main area.
- On Obsidian Mobile, running `Open workout editor for current file` from a clean state also opens in the main area.
- On Obsidian Mobile, running either command with a stuck drawer leaf (the user's current 0.4.1 state) detaches that drawer leaf and opens a fresh main-area leaf.
- On Obsidian Mobile, running either command while the editor is already open in the main area reveals that leaf (no duplicate, no detach).
- On desktop, running either command with no existing editor leaf opens a new tab in the main area; running either command while a main-area editor leaf exists reveals it (no duplicate).
- `npm run lint && npm run format:check && npm run build && npm test` pass on the final commit.
- PR carries the `patch` label.
- CHANGELOG `## [Unreleased]` lists the user-visible fix under `### Fixed`.

## 3. Context

### Why 0.4.1 didn't fix the bug on iOS

`src/main.ts:154-165` (current, post 0.4.1):

```ts
private async openWorkoutEditor(file: TFile): Promise<void> {
  /** Prefer a rootSplit leaf so both commands open in the main area on mobile, not in a drawer. */
  const leaves = this.app.workspace.getLeavesOfType(VIEW_TYPE_FITKIT_WORKOUT_EDITOR)
  const existing = leaves.find((l) => l.getRoot() === this.app.workspace.rootSplit) ?? leaves[0]
  const leaf = existing ?? this.app.workspace.getLeaf('tab')
  await leaf.setViewState({ type: VIEW_TYPE_FITKIT_WORKOUT_EDITOR, active: true })
  await this.app.workspace.revealLeaf(leaf)
  ...
}
```

Two bugs fall out of this on iOS:

1. **Stuck drawer leaf gets reused forever.** A user who had the editor open in a drawer before installing 0.4.1 (or whose first open under 0.4.1 happened to land in a drawer for some other reason) ends up with a `WorkoutEditorView` leaf whose root is `WorkspaceMobileDrawer`, not `workspace.rootSplit`. On the next `Open today's workout`, `leaves.find(rootSplit)` returns `undefined`, but `?? leaves[0]` falls back to the drawer leaf. `revealLeaf` then surfaces the drawer leaf in place. The `getLeaf('tab')` branch is never reached. The user's bug report on 2026-04-27 matches this exactly: they installed 0.4.1, the editor still opens in the drawer, every time.
2. **`leaf.getRoot() === workspace.rootSplit` may not hold reliably across mobile drawer leaves.** Codex flagged this in the post-merge review of 0.4.1. The Obsidian public API does not document drawer-root identity, and `iterateRootLeaves` is the canonical "main area only" iterator. Even if the comparison happens to work today, depending on it is fragile.

### Target behaviour

Use `iterateRootLeaves` to find a main-area editor leaf. Detach any other editor leaves (drawer leaves) so a stuck drawer leaf from before this fix gets cleaned up. Fall through to `getLeaf('tab')` when no main-area leaf exists.

```ts
private async openWorkoutEditor(file: TFile): Promise<void> {
  /** iterateRootLeaves only walks main-area leaves; detach any drawer leaves so a stuck mobile drawer leaf from before this fix is cleaned up. */
  let mainAreaLeaf: WorkspaceLeaf | null = null
  this.app.workspace.iterateRootLeaves((leaf) => {
    if (!mainAreaLeaf && leaf.view.getViewType() === VIEW_TYPE_FITKIT_WORKOUT_EDITOR) {
      mainAreaLeaf = leaf
    }
  })
  for (const leaf of this.app.workspace.getLeavesOfType(VIEW_TYPE_FITKIT_WORKOUT_EDITOR)) {
    if (leaf !== mainAreaLeaf) {
      leaf.detach()
    }
  }
  const leaf = mainAreaLeaf ?? this.app.workspace.getLeaf('tab')
  await leaf.setViewState({ type: VIEW_TYPE_FITKIT_WORKOUT_EDITOR, active: true })
  await this.app.workspace.revealLeaf(leaf)
  const view = leaf.view
  if (view instanceof WorkoutEditorView) {
    await view.loadFile(file)
  }
}
```

This satisfies all five of the success-criteria mobile cases (clean state, both commands, stuck drawer, already-open main area, repeat call) and preserves desktop behaviour.

### Why detach (not just ignore the drawer leaf)

If we ignore the drawer leaf and create a new main-area tab, the user ends up with two `WorkoutEditorView` leaves: one stuck in the drawer (still autosaving against the same file) and one in the main area. That is worse than the current state. Detaching the drawer leaf removes it cleanly.

`WorkoutEditorView.onClose` (`src/ui/workout-editor-view.ts:130-144`) clears the autosave timer and `await`s `flushAutoSave`, which writes any pending dirty edits before the leaf goes away. Two narrow edge cases worth knowing about, neither blocking:

- If a save is already in flight when detach fires, `flushAutoSave` returns early (`workout-editor-view.ts:1173-1175`); the in-flight write still completes asynchronously, so already-queued bytes land.
- If the leaf is dirty _and_ a disk conflict was detected, the conflict path skips the save (`workout-editor-view.ts:1181-1185`). The user's edit is dropped silently. This matches the existing user-initiated close behaviour, so detach does not regress anything; we simply inherit the same trade-off.

In practice the stuck drawer leaf this fix targets is one the user has not interacted with since installing 0.4.1, so there is no realistic dirty-with-conflict scenario at detach time. Documented here so future callers don't expect detach to be a hard guarantee that every edit is written.

### Why `iterateRootLeaves` over `leaf.getRoot() === workspace.rootSplit`

`iterateRootLeaves` is the publicly documented way to enumerate main-area leaves. `getRoot()` identity comparison is undocumented and depends on Obsidian's internal layout types behaving as we expect on every platform. Switching to `iterateRootLeaves` retires the fragile comparison entirely.


**Acceptance:**

- Gate passes.
- `git diff HEAD~..HEAD` shows only `src/main.ts` and `CHANGELOG.md` modified.
- `src/main.ts` diff: the import change on line 1, and the rewritten `openWorkoutEditor` body. No other edits.
- `CHANGELOG.md` diff: one new bullet under `## [Unreleased]` `### Fixed`.

**Risks:**

- `leaf.detach()` while the view has a pending autosave: `WorkoutEditorView.onClose` clears the timer and `await`s `flushAutoSave` (`src/ui/workout-editor-view.ts:130-144`). The two edge cases (in-flight save, dirty + conflict) are documented in §3 "Why detach"; neither blocks this fix.
- `iterateRootLeaves` callback signature: void return, no early-exit semantics. The `if (!mainAreaLeaf && ...)` guard inside the closure short-circuits after the first match; we accept the rest of the iteration as a no-op cost (small, and only runs on command invocation).
- Unlikely-but-possible: `getLeaf('tab')` on iOS still places the tab in a drawer in some workspace state. If the manual smoke shows this, the contingency is to add `app.workspace.setActiveLeaf(leaf, { focus: true })` after `setViewState` and before `revealLeaf`. Not in the first commit; revisit only if smoke fails.
