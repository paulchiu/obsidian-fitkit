## 1. Goal & Success Criteria

Ship a usable FitKit 0.1.0 that handles the three canonical workflows end-to-end against the existing dev-vault dataset:

1. **Structured editing:** open `<date>.md` workout note in a custom ItemView, edit sets/durations/notes, autosave to canonical Markdown (no data loss across reload).
2. **Journal import:** paste or open a rough journal note, preview canonical output, resolve unknown exercises interactively, write to a destination path.
3. **Local indexing & light reporting:** rebuild a JSON index over `Fitness/Workouts/`, regenerate the dashboard note with one section per known exercise.

**Definition of done for 0.1.0:**

- All 15 workouts in `/Users/paul/dev-misc/dev-vault/dev/Fitness/Workouts/` round-trip losslessly through parse → serialize → re-parse with semantic equality.
- All commands listed in §5 are wired and discoverable via the command palette.
- Editor ItemView is touch-usable in Obsidian mobile (manual smoke test, narrow layout < 600px).
- Vitest suite covers parser/serializer/registry/grammar with the fixtures listed in §7.
- `npm run lint && npm run format:check && npm run build && npm test` all pass clean.
- CHANGELOG `## [Unreleased]` lists user-visible changes; PR carries `minor` label.

## 2. Scope (In / Out)

**In for 0.1.0:**

- Workout note parser/serializer (Dataview inline fields, fenced-block preservation).
- Workout editor ItemView with autosave, conflict detection, mobile layout.
- Journal grammar parser + import modal with mapping UX.
- Exercise registry with alias normalization, bootstrappable from `Fitness/Exercises/*.md` stems.
- Local index: full vault scan to JSON cache, mtime-keyed.
- Dashboard generator: regenerate from index; track `hiddenDashboardSectionsByPath` so user-deleted sections stay deleted.
- Settings tab: fitness root path, journal folder, autosave debounce, auto-create-missing-exercises and auto-update-dashboard toggles.
- Commands listed in §5.
- Vitest fixtures lifted from real dev-vault notes.

**Out (defer to 0.2+):**

- LLM-assisted import.
- Merge conflict resolution UI (block-only mid-edit; reload banner is the v0.1.0 answer).
- SQL/WASM analytics.
- Custom fenced-code source format.
- "Repeat last workout" / "copy previous set" QoL features.
- Per-exercise unit overrides; multi-unit support.

### Phase 2 - Settings + plugin shell (sequential)

**Prereq:** Phase 1. **Output:** Plugin loads in Obsidian with a populated settings tab; no UI surfaces yet.

1. Define `FitKitSettings` type and defaults in `src/settings.ts`:
   ```ts
   export interface FitKitSettings {
     fitnessRoot: string;           // 'Fitness' (single source of truth for fitness data location)
     journalFolder: string;         // '' (empty allowed; not derived from fitnessRoot since journals live elsewhere)
     autoCreateMissingExercises: boolean; // false (default; see §8 Q1)
     autoUpdateDashboard: boolean;  // true; controls whether plugin-driven writes trigger index/dashboard refresh
     autosaveDebounceMs: number;    // 600
     exerciseRegistry: ExerciseRegistryEntry[]; // empty; bootstrap from vault on first run
     hiddenDashboardSectionsByPath: Record<string, string[]>; // keyed by dashboard path; per-section keys like 'exercise:Squat'
     schemaVersion: 1;
   }

   // Derived (not stored, computed on access):
   export function workoutsFolder(s: FitKitSettings): string;   // `${normalizePath(s.fitnessRoot)}/Workouts`
   export function exercisesFolder(s: FitKitSettings): string;  // `${normalizePath(s.fitnessRoot)}/Exercises`
   export function dashboardPath(s: FitKitSettings): string;    // `${normalizePath(s.fitnessRoot)}/Fitness Dashboard.md`
   export function workoutFilename(date: string): string;       // `${date}.md` (hardcoded YYYY-MM-DD)
   ```
   Single user-configurable root (`fitnessRoot`, default `Fitness`); workouts, exercises, and dashboard paths derive from it. Workout filename is hardcoded `YYYY-MM-DD.md`.
2. `loadSettings` / `saveSettings` via `Plugin.loadData/saveData`. On `schemaVersion` mismatch: full rebuild (drop cached registry, rescan).

Show a read-only "derived paths" preview block so the user can see where workouts/exercises/dashboard will land for their root choice. Group: "Paths", "Behavior".
4. Wire `loadSettings()` in `onload`, `saveSettings()` from settings tab. All path consumers run values through `normalizePath` and strip trailing slashes.

**Acceptance:** Plugin loads in Obsidian dev vault with no console errors; settings tab renders; values persist across reload.

### Phase 3 - Index + Dashboard (sequential before Phase 4)

**Prereq:** Phases 1, 2. **Output:** `Rebuild FitKit index` and `Rebuild FitKit dashboard` commands work end-to-end against the dev-vault.

> Phase 3 and Phase 4 both register commands in `main.ts`, both add CSS rules to `styles.css`, and both consume `settings`. Run them sequentially (3 then 4) on the same branch; do not parallelize.

1. **`src/index.ts`:** pure-ish module (takes `App` for vault read but logic is straightforward):
   ```ts
   export interface IndexEntry {
     path: string;
     mtime: number;
     date: string;
     name: string;
     exercises: ExerciseIndexRow[];
   }
   export interface ExerciseIndexRow {
     exerciseName: string;
     kind: ExerciseKind;
     bestSet?: { weight: number; reps: number; e1rm: number };  // strength only
     totalSets?: number;
     totalDurationSeconds?: number;  // duration only
   }
   export interface FitKitIndex {
     schemaVersion: 1;
     builtAt: number;
     entries: IndexEntry[];
   }
   export async function rebuildIndex(app: App, settings: FitKitSettings): Promise<FitKitIndex>;
   ```
   - Scan `settings.workoutsFolder`, filter `type: workout`, parse each, derive `bestSet` per exercise using **Epley e1RM** (`weight * (1 + reps / 30)`) with the tier rules in spec §10:
     - Tier A: max e1RM where reps in [1,12] and weight > 0
     - Tier B: max e1RM where reps ≥ 1 and weight > 0
     - Tier C: heaviest single set, or set with most reps if all weights are 0
   - Skip files that fail to parse; collect warnings into a returned diagnostics array.
   - Write `data.json` field `index` (or sibling `data-index.json` if it bloats settings).

2. **`src/dashboard.ts`:** generates `dashboardPath(settings)` content from index:
   - Top: PB summary list (one bullet per exercise: `**PB:** <weight>kg x <reps>`).
   - Per-exercise H2 section with a Dataview query block matching the patterns observed in `/Users/paul/dev-misc/dev-vault/dev/Fitness/Fitness Dashboard.md`. Exact template TBD (see §8 Q2).
   - Skip exercises whose key matches an entry in `settings.hiddenDashboardSectionsByPath[dashboardPath(settings)]`.
   - Idempotent: re-running produces byte-identical output for the same index.

3. **Auto-update on plugin-driven writes.** When `settings.autoUpdateDashboard` is true, the editor view (Phase 4) and the importer (Phase 5) must trigger an index refresh for the touched file and a dashboard regen on save success. Implementation: `index.ts` exports `updateIndexEntry(index, app, path)` for incremental updates; `dashboard.ts` exports `regenerate(app, settings, index)`. UI surfaces call these on successful write. Failure modes (parse error during update) surface via `Notice` and do not break the save.

4. Commands:
   - `fitkit:rebuild-index` - full vault scan; persist; `Notice` count of files indexed and warnings.
   - `fitkit:rebuild-dashboard` - rebuild dashboard from current index (full re-index first; no incremental detection in 0.1.0).
   - `fitkit:restore-hidden-sections` - clear `hiddenDashboardSectionsByPath[dashboardPath(settings)]`, regenerate.
   - `fitkit:show-parse-diagnostics` - modal listing warnings from last rebuild.

**Acceptance:** Running rebuild-index against the dev-vault produces a `FitKitIndex` with ≥ 21 distinct exercises and 15 workout entries. Dashboard generation writes a file with ≥ 21 H2 sections and the PB summary at top.

## 8. Open Decisions (bubble to user before Phase 5 lands)

These are unresolved in the spec or where dev-vault diverges from spec defaults. Each has a recommended default; user can override.

**Q1. Auto-create exercise notes?** When user adds an unknown exercise in the editor or import modal, should the plugin create `<exercisesFolder>/<Name>.md` automatically?
- (a) **Recommended:** No by default; `autoCreateMissingExercises: false`. User opts in via settings.
- (b) Yes by default.

**Q2. Dashboard template fidelity.** Should rebuild-dashboard produce queries that match the user's existing dashboard verbatim (PB list at top, per-exercise H2 with `## Recent Sessions` and `## Notes` Dataview blocks), or a simpler v0.1.0 layout?
- (a) Match existing fidelity (more code; round-trip the user's hand-curated dashboard).
- (b) **Recommended:** Simpler v0.1.0 layout (PB list + one query per exercise). User keeps hand-curated dashboard separate; plugin writes to `<dashboardPath>` only.

**Q3. Kind-switch confirm modal.** Switching strength → duration on an exercise card with existing rows: confirm?
- (a) **Recommended:** Confirm if any rows exist; bypass if card is empty.
- (b) Always confirm.
- (c) Never confirm; data loss on switch is the user's problem.

**Q4. "Add 'Foo'" suggestion in editor.** When user types unknown exercise name in the editor (not the importer), what does "Add 'Foo'" do?
- (a) **Recommended:** Add card only; do not create exercise note. (Importer is the place that creates notes.)
- (b) Create card and stub exercise note.

**Q5. ~~Folder defaults~~:** resolved by single-root `fitnessRoot` setting (default `Fitness`). User edits one value if their vault uses a different root.

**Q6. README in 0.1.0.** Rewrite README with usage docs, or ship 0.1.0 with minimal README and document in 0.2?
- (a) **Recommended:** Rewrite for 0.1.0 (helps BRAT users).
- (b) Defer to 0.2.

**Q7. Fixture provenance.** The dev-vault is the user's personal vault. Are workouts in `tests/fixtures/workouts/` OK to commit publicly? They contain dates and weights but no PII.
- (a) **Recommended:** Commit verbatim; data is non-sensitive.
- (b) Anonymize dates / synthesize fixtures from scratch.

**Q8. Coexistence with `workout-log` plugin.** Spec says preserve fenced code blocks verbatim. Should v0.1.0 also avoid registering on files that contain a `workout-log` fence, or is preservation enough?
- (a) **Recommended:** Preservation is enough; do not gate the editor view.
- (b) Skip editor view on files that contain a `workout-log` fence.

## 9. Risks

- **Vitest + esbuild target mismatch.** Test files import TS modules transpiled differently than the bundle. Mitigation: confirm Vitest targets match `tsconfig.json` `target: ES2018`; pure modules use no ES2019+ features.
- **Mobile flake.** ItemView sizing on iOS Obsidian can be quirky. Mitigation: manual smoke test before shipping; defer fancy interactions to 0.2.
- **Index size.** Stuffing the full index into `data.json` works for the dev-vault but may bloat for power users. Mitigation: write to a sibling `<plugin>/index.json` if `data.json` exceeds 100KB; for 0.1.0, single file is fine.
- **Lift drift.** POC files use 2-space already (most), but may have stacked `//` comments or non-named exports. Phase 1 must apply AGENTS.md style without rewriting logic.
- **Schema migration.** `schemaVersion: 1` is the only version. If the parser changes mid-0.1.0 development, set to 2 and force rebuild.
